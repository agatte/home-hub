# Future Development Registry

Use `docs/Future_Development.md` as the durable research brief and idea registry.
Read its intro/status vocabulary/promotion flow plus only the relevant job sections;
read the full registry for a broad scan.

Classify ideas using the registry's existing vocabulary such as `TRACKED`,
`FOLDS INTO`, `CANDIDATE`, `LAB`, or `PARKED`. Mark immature techniques `LAB`.
Do not create a new issue merely because an idea is interesting; prefer an
existing owner when one already fits.

When updating the registry, place the idea under the correct job, retain useful
concept detail even when it folds into an existing issue, and update cross-links
instead of duplicating prose. Refresh the review date only when the research
checkpoint materially changes.

Do not update `docs/PROJECT_SPEC.md` unless accepted cross-system product policy
actually changes. A registry edit does not itself authorize implementation,
deployment, device writes, or a GitHub issue creation.

For a durable research checkpoint, record the useful finding, HomeHub fit,
ownership/dedupe, purchase cost class, evidence/uncertainty, and the smallest
next experiment or observation.
