# Full System Audit — 2026-05-05

Comprehensive audit pass across backend services, ML systems, frontend,
security, and lighting design. Three Explore agents produced ~110 raw
findings; verification against the actual code reduced that to ~75
real items. This doc records:

1. **What shipped** — high-level summary by phase
2. **False positives** — agents flagged it, code was already correct (saved
   so future audits don't re-flag the same items)
3. **Deferred to backlog** — real but low ROI; revisit if/when relevant
4. **Open follow-ups** — tracked decisions with deadlines

Authoritative source for architecture/scope: `PROJECT_SPEC.md` + `ML_SPEC.md`.

## Deferred to backlog

Real findings, but ROI didn't justify shipping in this audit. Documented
here so they can be picked up if/when relevant.

### Backend / services

- **WeatherService alert dedup** — Severe alert descriptions are read every
  2 min while active even when the alert ID hasn't changed. Re-fires the
  same effect-overlay decision repeatedly. Fix direction: hash alert ID,
  only fire on novelty. Low impact: alerts are rare and the redundant
  reads don't burn user-visible cycles.
- **HueService input validation** — `set_light` doesn't validate the state
  dict keys/values (e.g. `{"on": "true"}` as a string, `{"bri": 999}`
  out of range). The bridge already rejects bad payloads silently;
  improving error surfacing is a nice-to-have, not a fix.
- **PiholeService 401 retry edge case** — On re-auth failure, the original
  401 still raises through `raise_for_status()` with a confusing error.
  Only fires if the original was 401 AND re-auth fails AND something
  in the retry path raises — multi-condition tail event.
- **Schema drift between `models.py` and migrations** — `_run_migrations()`
  creates `ml_decisions` / `ml_metrics` via raw SQL while the model
  classes are SQLAlchemy. New tables added in only one place could be
  missed on fresh installs. Production deploys via `git pull`, not
  fresh installs, so the bite radius is small.
- **PC agent `GAMING_IDLE_THRESHOLD` undocumented** — Late-night gaming-
  stuck-on case isn't in production failure logs but the threshold
  semantics aren't fully spelled out in the code. Pin them in CLAUDE.md
  if the case ever surfaces.
- **DST backfill in `ml_logger.backfill_actual_range`** — Window math uses
  naive UTC for the comparison; could mis-window across an Indianapolis
  DST boundary. Fires twice a year, low impact.

### Frontend

- **Light-command optimistic rollback** — `init.js:155-156` patches the
  light store optimistically; if the WS send fails, the optimistic state
  sticks. Low frequency in practice (LAN WS is reliable). Fix direction:
  on `connection_status` reconnect, refetch `/api/lights`.
- **Mode lock timeout race** — `init.js:90-94` clears the lock on the 2s
  timeout instead of only on confirmation. A late-arriving WS update
  can flip the UI back. Fix direction: tag commands with epoch-ms request
  IDs and only resolve on matching response.
- **Bundle size / Three.js chunk** — `DAohpB6Z.js` is 705 kB pre-gzip
  (184 kB gzipped). Threlte + Three for the moon scene. Code-split if
  it shows up in real-world load times.
- **Color contrast on glass cards over animated backgrounds** — Borderline
  4.5:1 in bright aurora regions. Punt unless it surfaces as a complaint.
- **Bundle-size monitoring CI** — Would catch creep but no monitor in
  place. Add only if bundle creep becomes a problem.

### ML

- **MLDecisionLogger broadcast dedup** — Every fusion result broadcasts
  via WS even when identical to the previous one. With 2 active clients
  this is a non-issue; with 10+ it'd be worth a `_last_payload` cache.
- **MusicBandit corrupted-state distinction** — `_load_failed=True`
  collapses to uniform random with no clear `/health` signal. Fix
  direction: surface `music_bandit: {status: "load_failed", path: ...}`
  in the health payload.
- **LightingLearner stale-data cleanup** — Preferences load once at boot;
  no recompute. A weekly task that recomputes from the last 60 days of
  `light_adjustments` would keep preferences fresh as taste drifts.
  Currently fine because Anthony's preferences don't drift fast.
- **ML lane heartbeats on `/health`** — `/health` already shows poll-loop
  staleness via `tasks[]`; per-lane heartbeats (process / camera /
  audio_ml / rule_engine reported `last_signal_at_utc + age_seconds`)
  would make "is the lane firing?" answerable from a single GET. Worth
  doing once the audio gate decision lands and lane membership is final.

## Open follow-ups (with deadlines)

These have decision points, not just punts. Calendar them.

### Audio classifier `speech_multiple` gate — 2026-05-09 decision

The gate is structurally unreachable in production:

- 2026-05-03 36-hour checkpoint logged 0 firings, including a multi-person
  guest visit
- YAMNet's actual class outputs don't reliably score `speech_multiple` at
  ≥0.80 confidence in real living-room acoustics
- Memory: `project_audio_classifier_shadow_followup.md`

**Three options:**

1. **Retarget the gate** — Map to YAMNet classes that DO score (e.g. `Speech` + `Crowd` co-occurrence rule similar to the existing `tv_dialog` pattern)
2. **Retrain a small head** — Collect labeled audio from real social events + train a binary classifier; ~2-week effort
3. **Abandon the audio social gate** — Lean on manual override + process detection only. Simplest; loses the "automatic dim-the-lights when guests arrive" goal.

`MODE_THRESHOLDS["speech_multiple"]` stays in `audio_classifier.py` as
documentation until the decision lands.

### Predictor v1 → v2 validation — 2026-05-11 fire

Memory: `project_step5_predictor_validation.md`. After a week of shadow
predictions at the new low-confidence-tagging:

- Read accuracy on `low_confidence: false` rows

### Predictor v2 motion features — defer until v1 validation
